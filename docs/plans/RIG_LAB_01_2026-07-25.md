# Rig Lab 01: Mobility and Capability Translation

- Date: 2026-07-25
- Status: **Complete for the local evidence contract**
- Owner: project owner
- Implementation decision: [ADR-0006](../decisions/ADR-0006-rig-capability-portability.md)
- Risk class: low; local browser gameplay prototype with versioned local persistence
- Evidence target: Tier 4 local runtime observation

## Product hierarchy

Rigs Unbound is a vehicle-driven universe spanning many vehicle types, worlds, scales, perspectives, and mechanics. No single vehicle, world, activity, perspective, or mechanic defines the product.

The persistent abstraction under test is:

```text
Rig
- profile and mobility adapter
- capabilities
- attachments
- world rules
- activity contract
- condition and evolving history
```

Field Test 001 remains useful tractor evidence. It is not the roadmap center.

## Question

Can one canonical gameplay path make a utility tractor and toy buggy feel materially different while both complete an activity composed from a shared towing capability?

The test fails if:

- either rig requires a second input, save, camera, activity, or world-interaction pipeline;
- the activity branches on a rig name rather than a capability;
- the buggy is only a differently shaped tractor;
- migrating the save discards the existing tractor history;
- performance evidence is asserted without direct measurement.

## Implemented evidence

### Contrasting rigs

- **Torque / utility tractor**
  - high mass;
  - stable towing;
  - lower maximum speed;
  - slower steering response;
  - field-plough and tow-hook attachments.
- **Spark / toy buggy**
  - low mass;
  - high acceleration and maximum speed;
  - faster steering response;
  - larger towing penalty;
  - tow hook and jump capability;
  - a lower/closer camera profile.

Both consume the same `InputFrame`, `stepGame`, camera modes, public state, fixed-step clock, save schema, and renderer adapter.

### Shared capability and activity

The cargo relay is one stateful workflow:

```text
ready
  -> capable rig approaches cargo
  -> primary semantic action attaches through tow capability
active
  -> cargo follows the persistent rig hitch
  -> movement remains profile-specific
  -> delivery gate queries cargo position
complete
  -> cargo detaches
  -> completion and best time persist
```

The tractor may plough when there is no reachable tow target. Spark cannot plough because the profile does not advertise that capability.

### Mobility contrast

The same ground-controller adapter reads profile data for:

- acceleration and reverse acceleration;
- forward and reverse limits;
- drag and braking;
- steering response and turn rate;
- wheel radius;
- mass and tow stability;
- tow-speed multiplier;
- jump impulse and landing tolerance;
- chase camera policy.

The relay ramp queries the `jump` capability. It does not query the buggy id.

### Persistence

Save schema v2 owns:

- active rig id;
- both persistent rig states;
- each rig's attachment state, condition, and history;
- cargo-relay state;
- shared world memory and presentation state.

A valid v1 tractor save migrates into the Torque entry. Spark and the relay receive valid initial state. Invalid saves still recover to a clean record with a player-visible explanation.

### Instrumentation

The browser exposes:

- time to first controllable frame;
- rolling average and p95 frame time;
- derived FPS;
- draw calls and triangles;
- JavaScript heap when Chrome exposes it;
- load duration;
- last save duration and serialized size.

The values are available in the HUD summary, `window.render_game_to_text()`, and `window.getPerformanceSnapshot()`.

## Acceptance contract

### Player behavior

- Enter one world and see two persistent rigs.
- Switch rigs with `R` or the touch action.
- Feel visibly different acceleration, speed, steering, camera, and tow response.
- Approach cargo and use one semantic capability action to attach it.
- Deliver cargo to the cyan relay gate and receive a timed completion result.
- Drive Spark over the ramp and become airborne.
- Use Torque's plough when cargo is not the active target.
- Reload without losing both-rig history or relay completion.
- Reset both rigs, activity state, and world memory through one explicit confirmation.

### Architecture

- Simulation and state do not import Three.js.
- One action path and one state path serve both rigs.
- World interactions query capabilities.
- Rig profiles are versioned product configuration and covered by tests.
- Renderer nodes never enter state or persistence.
- The current `ground` mobility adapter is explicit; it does not claim to model flight, water, tracked, articulated, or bicycle behavior.
- Existing v1 state has a deterministic v2 migration.

### Verification

- strict TypeScript check;
- live state-kernel and preserved experiment tests;
- formatting check;
- production build;
- visible Chrome cargo/jump/reload workflow;
- desktop and `390 × 844` screenshot inspection;
- console and page-error inspection;
- exported local performance snapshot.

## Explicit boundaries

- This is not a final engine decision.
- It is not representative-player proof that both rigs are fun.
- It is not a production performance benchmark.
- It does not prove bicycle, tracked, water, aircraft, rocket, or spacecraft controllers.
- It does not add a physics engine, collision system, camera occlusion, replay recorder, cloud save, account, analytics backend, or public deployment.
- It uses project-owned primitive geometry and no raw private Kenney assets.

- Recorded the decision in ADR-0006 before the implementation refactor.

Outcome: the first coherent portability stage is on the long-term product path without attempting a universal vehicle engine.

Outcome: the result is reviewable as local Tier 2–4 evidence and is explicitly not launch-ready.

## Anything else?

Yes. Numerical handling contrast is necessary but insufficient. The next player-evidence question is whether people describe Torque and Spark with different verbs and emotions after driving them. If they do not, profile values and silhouettes must be tuned before adding more rigs.
