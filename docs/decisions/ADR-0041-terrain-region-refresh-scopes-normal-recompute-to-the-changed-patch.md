# ADR-0041 — Terrain region refresh scopes normal recompute to the changed patch

- Date: 2026-07-29
- Status: **Implemented and verified for the current runtime.** This is a reversible technical correction inside an existing rendering contract (`ADR-0007`'s "what you see is what you can hit"), not a load-bearing product/architecture/authority/economy/irreversible-policy decision, so it does not require the ADR-first operator-sign-off gate (`motto_v4.md` §0.12.2). It is recorded per the "everything is a documentation candidate" rule (`motto_v4.md` §0.3.1) because it is a real audit finding, a root-cause fix, and a performance-relevant runtime change.
- Owner: Rigs Unbound presentation shell
- Affected runtime: `src/game/renderer.ts`, `src/game/performance.ts`
- Related evidence: `src/game/renderer-terrain-normals.test.ts`, `docs/decisions/ADR-0007-terrain-as-simulation-substrate.md`
- Requested by: operator, via the `threejs-performance` skill audit requested in-session and the explicit instruction to "run it properly, get the full audit report," followed by "do everything properly long term 1st principles, motto_v4 aligned."

## Context

An in-session audit (using the `threejs-performance` skill, `~/.agents/skills/threejs-performance`) against `src/game/renderer.ts` found that `refreshTerrainRegion()` — called from `render()` on every terrain-deformation tick, i.e. continuously while a player holds the plough control — ended with `this.terrainMesh.geometry.computeVertexNormals()`. `THREE.BufferGeometry.computeVertexNormals()` has no partial mode: it always walks every triangle in the mesh, regardless of how much geometry actually changed.

The terrain mesh is a `TERRAIN_SPAN / TERRAIN_STEP ≈ 524m / 5.2m ≈ 102×102` vertex grid (`world.ts`'s `WORLD_RADIUS`, `renderer.ts`'s `TERRAIN_SPAN`/`TERRAIN_STEP`), ~20,402 triangles. A single plough tick only re-samples heights inside a 9m-radius box around the active rig (`refreshTerrainRegion(x, z, 9)`), which is roughly a 5×5 vertex patch — about 0.6% of the mesh. The full-mesh normal recompute was therefore doing ~166x more work than the change required, on every tick, in the hot ploughing path.

Measured cost, using this repo's own `three` dependency (not a synthetic library): a full `computeVertexNormals()` call on a 102×102/20,402-triangle grid costs 10–25ms depending on machine load (measured both via a standalone Node benchmark and via the actual shipped function, see Evidence). This repo's own frame budget (`runtime-profile-policy.ts`): `maximumAverageFrameMs: 25`, `maximumP95FrameMs: 33.4`. A single call at the low end of the measured range already consumes ~40% of the average-frame budget to recompute geometry that mostly didn't change.

This directly works against `renderer.ts`'s own stated goal in its file header — "what you see is what you can hit" — by spending render-path budget disproportionate to the actual change, on a path (ploughing) this repo already treats as gameplay-critical (`ADR-0007`, `terrain.ts`'s ploughing-order composition doctrine, `world-memory.test.ts`'s ploughing tests).

## Decision

1. Add `refreshTerrainNormalsInRegion()` (exported, pure — takes `THREE.BufferAttribute` position/normal plus the grid geometry parameters, no `this`/class dependency) that recomputes vertex normals only for the changed vertex box plus a one-vertex padding ring, using the **exact same accumulation algorithm** `THREE.BufferGeometry.computeVertexNormals()` uses internally (unnormalized cross-product accumulation per triangle corner, then per-vertex normalize — verified by reading `node_modules/three/src/core/BufferGeometry.js` directly rather than assuming the algorithm). This is a scoping change, not an approximation: a partial run and a full run produce numerically identical normals for every vertex, proven by test (see Evidence).
2. The function separates two regions, not one: the **write region** (vertices whose normal is zeroed and rewritten — the changed box padded by one ring) and a wider **source region** (cells read to rebuild those normals — padded by one more ring, because a write-region boundary vertex needs the contribution of its one unchanged neighbouring cell too). The accumulate step reads from the source region but only ever writes to a vertex inside the write region, so untouched neighbouring geometry is never double-counted or corrupted.
3. `refreshTerrainRegion()` now calls this function instead of `computeVertexNormals()`, with a defensive fallback to the full recompute if the terrain mesh's `normal` attribute is missing or mismatched in size (not expected to run in the live game — `buildTerrain()` always creates a matching normal attribute before any `refreshTerrainRegion` call is reachable).
4. Added `terrainRegionRefreshMs` end-to-end through `RendererMetrics` → `PerformanceSnapshot` → `renderer.metrics()`, following the exact existing pattern `terrainBuildMs` already establishes, so the cost of this path is observable at runtime rather than only known from a one-time audit (`motto_v4.md` §0.10, observability is delivery).

## Options considered

- **Leave `computeVertexNormals()` as-is, accept the cost**: rejected — it is a real, measured, disproportionate cost on a hot gameplay path, and `motto_v4.md` §6 ("pre-existing is not an excuse") means finding it during an audit and not fixing it is not an option.
- **Reduce `TERRAIN_STEP` resolution instead (cheaper full recompute via fewer triangles)**: rejected — this would degrade the terrain mesh's actual geometric fidelity everywhere to reduce the cost of a locally-scoped operation; it fixes the symptom by making the whole mesh worse, not the actual mismatch between the height update's scope and the normal update's scope.
- **Skip normal updates entirely for a few frames and batch them (temporal throttling)**: rejected — this would reintroduce the exact "physics deforms, render lags" incoherence `refreshTerrainRegion`'s own docstring already exists to prevent ("without this the ground would deform for physics while looking untouched, which is the worst of both"). Scoping the *work*, not delaying it, keeps the existing coherence guarantee intact.
- **Approximate normals for the patch (e.g. reuse neighbouring normals, cheaper but not identical)**: rejected — an approximation is a second, subtly different lighting model living beside the real one, which is exactly the kind of duplicate-truth pattern `motto_v4.md` §7 (Supersession) and this repo's own renderer docstring (single source of visual truth) argue against. Reimplementing Three.js's own exact algorithm, scoped, costs the same design effort and has zero fidelity loss.
- **Chosen: scope the existing exact algorithm to the changed region** — matches the height-update code immediately above it in the same function, which already does exactly this (`for (iz = minIz..maxIz) for (ix = minIx..maxIx)`); extending the same discipline to normals is the coherent, minimal, first-principles fix, not a new architecture.

## Evidence

- **Tier 1 (static/typecheck)**: `npm run typecheck` passes clean (`tsc --noEmit` plus the `deterministic-kernel-probe` sub-project typecheck), including the one call site (`runtime-profile-policy.test.ts`'s `PerformanceSnapshot` fixture) that needed the new required field added — fixed at the root (added the field to the fixture), not by making the type optional (`motto_v4.md` §22).
- **Tier 2 (targeted tests)**: `src/game/renderer-terrain-normals.test.ts`, 4 tests, all passing:
  1. Partial recompute matches a full `computeVertexNormals()` recompute **for every vertex in the mesh** (not just the touched patch) after a representative multi-vertex deformation — this is an equivalence proof, not a smoke test, and it is what caught a real bug during implementation (see "Anything else?" below).
  2. Partial recompute does not write to any vertex outside the changed box's one-vertex padding ring (sentinel-value test).
  3. The padded region correctly clamps at a grid edge/corner (`minIx=maxIx=minIz=maxIz=0`) without throwing and produces a finite, unit-length normal.
  4. Partial recompute matches a full recompute when the deformed box touches the opposite far corner of the mesh (`size-1, size-1`), covering the other clamp direction.
- **Tier 2/3 (regression)**: full existing suite, `npx vitest run` — **75 files, 471 tests, all passing**, no regressions in `terrain.test.ts`, `world-memory.test.ts` (ploughing-specific tests), `route-opening.test.ts`, or any other file. One non-fatal `Unhandled Rejection: Channel closed` / `ERR_IPC_CHANNEL_CLOSED` was observed in the worker-pool teardown after all tests completed (exit code 0); this looks like Vitest/tinypool worker-shutdown noise on this large a suite, not a test failure — flagged here rather than silently dropped, not root-caused further because it did not affect the pass/fail outcome and is outside this change's blast radius.
- **Real-world benchmark (not synthetic)**: using this repo's actual `node_modules/three` and the actual shipped algorithm (re-derived inline from `renderer.ts` for the benchmark script, matching the real grid size `Math.round(TERRAIN_SPAN / TERRAIN_STEP) = 101` cells): full `computeVertexNormals()` on the real grid size measured 10.1–24.6ms across two runs (machine load varied between runs); the new scoped function on a realistic ~9m plough-radius box measured 0.37ms — roughly a **30–66x** reduction for a representative single plough tick, consistent with the ~0.6%-of-mesh-changed estimate.
- **Tier 4 gap, stated explicitly (as of first pass, 2026-07-29)**: I could not get sustained "drive forward + plough" interactive input to register through the automated browser tool in this session (0 km/h reported after ~350 simulated keypresses; the app itself loaded and rendered with zero console errors both at idle and under that input load, so this looks like a browser-automation input-timing limitation, not a game defect). **What remains unverified**: the actual in-browser visual result of ploughing with this change — no lighting seam at the patch boundary — has not been directly observed by a human or an agent watching the live canvas. **Exact manual check needed next**: run `npm run dev`, drive the tractor (`WASD`) onto soft ground, hold `Space` to lower the blade, plough a furrow, and visually confirm no lighting discontinuity at the edge of the deformed patch, from at least one oblique low-angle camera view (where a normal seam would be most visible). The equivalence test (Tier 2, item 1 above) makes a visual defect very unlikely — the partial and full recompute produce numerically identical normals for every vertex, not just the patch — but "very unlikely by proof" is not the same evidence tier as "observed," and `motto_v4.md` §0.2 requires stating that difference plainly rather than rounding it up to full confidence.
- **Tier 4 gap closed (same-day follow-up, 2026-07-29)**: root-caused the automation limitation instead of working around it — the game's `InputController` (`src/game/input.ts`) tracks genuinely-held keys via real `window` `keydown`/`keyup` `KeyboardEvent`s, and the browser tool's synthetic "key press" action sends an instant keydown+keyup pair per invocation, never a sustained hold, so `held` never accumulated. Separately, `document.hasFocus()` was `false` until a real trusted click landed on the page (confirmed by direct inspection: `false` before a genuine click, `true` after). Fix for verification purposes: one real trusted click (via the browser tool's `computer` action, not scripted) to grant document focus, then dispatched genuine `KeyboardEvent('keydown', ...)`/`keyup` pairs via `javascript_tool` with real wall-clock time elapsed between them (`computer wait`) — the same event type and shape the game already listens for, held for a real duration the way an actual player's held key would be. This produced real, sustained driving (0 → 25 km/h) and a real plough ("Field plough lowered. Soft ground will hold the cut.", `CAPABILITY: Ploughing` in the HUD, `SURVEYED` ticking up). Observed through this live session, with the patched code actually running: **zero console errors, zero dev-server errors**, across drive + plough + camera-angle changes (Chase, Side, Top-down, Hood) including a dusk/"GLOAM" grazing-light angle (the most diagnostic lighting condition for a normal-seam defect, since low-angle light exaggerates shading discontinuities) — no visible lighting seam, no black triangles, no z-fighting, no flicker at the ploughed patch boundary in any observed frame. This raises the evidence tier from Tier 3 to **Tier 4 (runtime/manual behavior observed)** for the visual-correctness claim; it does not raise it to Tier 5 (production-like/real-data verification at scale — e.g. many consecutive plough ticks across a full session, or a side-by-side diffed screenshot rather than an eyeballed one), which remains open if a stricter bar is ever wanted.

## Consequences

- Ploughing-tick cost drops from a full-mesh normal recompute to one proportional to the actual changed area, closing the real budget-consumption gap identified in the audit.
- The scoped algorithm is a pure, independently-testable function (`refreshTerrainNormalsInRegion`), separate from the `GameRenderer` class's WebGL-context-dependent construction — this is also a small, justified architectural improvement (motto_v4 §21: code is evidence, not a boundary; correct the mechanism when a decision changes it), since it is the only part of `renderer.ts` that is now unit-testable without mocking a WebGL context, and that testability is precisely what let the equivalence bug below get caught before shipping.
- `terrainRegionRefreshMs` is now available on every `PerformanceSnapshot`, extending existing observability infrastructure rather than adding a new one.

## Anything else? (motto_v4 §0.1.1 standing review prompt)

- **A real bug was caught by the equivalence test, not by review.** The first implementation zeroed the padded write-region's normals but only re-accumulated contributions from cells whose *geometry* had changed, not from every cell that *touches* a write-region vertex — so boundary vertices lost the contribution of their one unchanged neighbouring cell and produced normals that differed from a full recompute by a non-trivial amount (~0.04, well outside float tolerance). This is exactly the class of error `motto_v4.md` §0.2 (confidence honesty) warns about: the code looked correct, compiled clean, and matched my own mental model on first write — it was wrong anyway, and only the equivalence test (not typecheck, not code review, not the boundary/sentinel test) caught it. The fix (source region one ring wider than the write region, with per-vertex write-gating) is recorded in the function's own doc comment so a future reader does not have to rediscover this the hard way.
- **Should the same scoping problem exist anywhere else in `renderer.ts`?** Checked: `buildTerrain()`'s own `computeVertexNormals()` call (full-mesh, one-time at construction) and `rebuildTerrainHeights()`'s call (full-mesh, only on a full reset) are both legitimately full-mesh operations — the entire grid genuinely changes in both cases, so there is nothing to scope. No other per-frame or per-tick full-mesh geometry operation was found in this pass; the audit's other findings (draw-call discipline, per-frame allocation, shadow/texture strategy) were already clean, as reported before this fix began.
- **Does this change any public contract?** No — `refreshTerrainRegion`'s signature, `renderer.metrics()`'s existing fields, and the terrain mesh's visual/physical behavior (heights, and now-verified-identical normals) are unchanged. Only the *cost* of producing that unchanged result changed, plus one new optional-shaped metrics field.
- **Nothing was committed to git.** Per `motto_v4.md` §3/§17 and the operator's standing git-safety instruction, these changes are implemented, tested, and documented, but staged/committed only on explicit request.
